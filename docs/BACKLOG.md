## Shipped this session (tracking chip — Phase 4's first intel gadget)

- **Tracking chip** (`item.TrackingChipItem` + `item.TrackingChipTarget`, all `common`): reverse-engineered from a `transmitter`, the first of the doc's "electronics / intel gear" line (see `DESIGN.md`: "tracking chips let you mark valuables and follow them"). Deliberately narrow — it only ever tracks the *one* target the player personally marked, not an always-on radar, per the "does NOT trivialize the horror" brief.
  - **Tag**: `useOnEntity` marks any right-clicked `LivingEntity` (tagging yourself is a no-op `ActionResult.PASS`, not an error); `use()` (air click) first tries a short (4.5-block) entity raycast — reusing `ChargeLaserItem`'s proven `ProjectileUtil.getEntityCollision(world, user, start, end, box, predicate)` idiom at a much shorter range — to catch a nearby dropped `ItemEntity`, since `useOnEntity` never fires for non-`LivingEntity` targets. Either path writes a `TrackingChipTarget` (target UUID + last-known x/y/z) onto the stack and glows the target.
  - **Read**: `use()` falls through to a read when the short raycast finds nothing. Resolves the stored UUID via `ServerWorld#getEntity` (loaded-entities-only lookup, same call `FireMissionManager`/`GuidedMissileEntity` already use); if found, refreshes the stored position, re-glows, and prints `Bearing <N/NE/.../NW> · <n>m` to the actionbar (`player.sendMessage(text, true)`); if not found (unloaded chunk or dead-and-gone), prints "Signal lost" and leaves the last-known position on the stack rather than clearing it.
  - **Glow**: `LivingEntity` targets get the real `StatusEffectInstance(StatusEffects.GLOWING, 600, 0)` (30s, auto-expires, matches the `ProgramDroneEntity`/`BatteryCenterEntity`/`ScanPlayerGoal` 3-arg constructor already used in this repo). A dropped `ItemEntity` isn't a `LivingEntity` and can't take status effects, so it gets the underlying `Entity#setGlowing(true)` render flag directly instead — **documented simplification**: unlike the status effect, that flag has no built-in timer, so a tagged item stays glowing indefinitely (until re-tagged/despawned) rather than fading after 30s like a tagged mob does. Noted in the class doc, not hidden.
  - **Data component**: `P7DataComponents.TRACKING_CHIP_TARGET` (`ComponentType<TrackingChipTarget>`), registered the same direct `Registry.register` way as `CHARGE_LASER_STATE` (no `DeferredRegister` — `DATA_COMPONENT_TYPE` is static). `TrackingChipTarget`'s codec uses `Uuids.CODEC` for the UUID field (unverified against a sibling use in this repo — see below) plus three `Codec.DOUBLE` fields for the position, and `PacketCodecs.registryCodec(CODEC)` for the packet codec, mirroring `ChargeLaserState` exactly per the repo's hard-won lesson about that wrapper. No default component value is set on a fresh stack — `stack.get(...)` returning `null` *is* "no signal," rather than wrapping the payload in an `Optional`.
  - **Recipe**: shapeless, `transmitter + redstone + copper_ingot → 1 tracking_chip` (first shapeless recipe in this repo — every existing recipe here is `crafting_shaped`; the JSON shape itself is standard vanilla `minecraft:crafting_shapeless`).
  - **Model**: new `models/item/tracking_chip.json`, the same `minecraft:block/block` + flat-swatch-material pattern as `drone_core.json`/`transmitter.json` — a small slab body, an inset cyan "die," two dark crossing trace grooves, and four grey corner leads (IC-chip silhouette). Reuses four **already-shipped** material swatches (`mat_3c414a`, `mat_34e8da`, `mat_646b78`, `mat_2e323a`) — no new texture file needed, so there's nothing new to visually verify on the texture side, only the geometry.
  - **Sound**: one new event (`item.tracking_chip.ping`), registered in `P7Sounds`/`sounds.json` redirected to the existing `block.amethyst_block.chime` vanilla placeholder (same one `LASER_LENS_WARN` already uses), plus a subtitle. Played on both tag and re-read, `SoundCategory.PLAYERS` (a personal cue — deliberately *not* routed through `ProgramAcoustics.reportNoise`, so reading your own chip doesn't alert nearby drones).
  - **Not verified / most worth a second look**: (1) `Uuids.CODEC` being a `Codec<UUID>` at `net.minecraft.util.Uuids` — recalled from memory, not cross-checked against any existing use in this repo (there was none); (2) `Entity#setGlowing(boolean)`/`isGlowing()` existing at the base `Entity` level (not `LivingEntity`) — needed for the dropped-item glow path; (3) `ActionResult.PASS` — the repo only had precedent for `SUCCESS`/`CONSUME` before this change; (4) `PlayerEntity#sendMessage(Text, boolean)` for the actionbar readout — used per the task brief's own explicit signature, not cross-checked against a sibling call in this repo (there was none). ## Shipped this session (ender pearl launcher — a long-range warp tool)

- **Ender pearl launcher** (`item.EnderPearlLauncherItem`, all `common`): a battery-powered, charge-up gun that lobs a *vanilla* `EnderPearlEntity` a very long distance. Vanilla ender pearls already teleport their thrower on impact — this class never touches teleport logic, it just launches a real pearl hard enough that a well-aimed shot is a precision, long-range blink across the map instead of the usual short toss. Not a boss-killer or a combat weapon: it deals no damage, its cost is the battery economy plus the charge-up window (you're exposed while charging).
  - **Charge-up**: the bow/trident `use()`/`usageTick()`/`onStoppedUsing()` idiom (72000-tick max use, same shape `ChargeLaserItem` uses). Holding right-click builds charge linearly over `CHARGE_TICKS_TO_FULL` (40 ticks); releasing below `MIN_CHARGE_FRACTION` (20%) is a soft click — no shot, no battery spent. At/above that, launch speed is `MathHelper.lerp(chargeFraction, 0.3, 3.5)` blocks/tick along the look vector — the same curve the laser sight previews live, so what you see charging is what you get on release.
  - **The pearl**: `new EnderPearlEntity(serverWorld, player)` (vanilla constructor, owner set so vanilla's own teleport-on-impact fires normally) with `setVelocity(look.x*speed, look.y*speed, look.z*speed)` (the plain 3-arg `Entity#setVelocity`, the same public method `GlowStickEntity#launch` already uses in this repo) — no custom physics, no reimplemented teleport.
  - **Laser sight**: `usageTick` forward-simulates the pearl's *own* physics every 2 ticks at the *current* charge speed — drag then gravity, mirroring `ThrownEntity`'s integration order the same way `BallisticSolver`'s doc describes (reuses `BallisticSolver.DRAG` directly; gravity is a local `0.03` constant matching that class's documented "un-overridden ThrownEntity default," since vanilla `EnderPearlEntity` never overrides `getGravity()`). This is a custom stepped forward sim, not `BallisticSolver.solve()` itself — that method solves the *inverse* problem (given a target, find launch velocity), which doesn't fit "given the current charge, where would it land." Each simulated tick is a cheap `!getBlockState(...).isAir()` check (not a full raycast) to bound the cost of up to 200 simulated ticks; only the final short segment gets one precise `World#raycast` to pin the exact impact point, and a single `ProjectileUtil.getEntityCollision` search runs once over the whole resolved path (not once per tick) so a mob in the arc can pre-empt the block landing. Drawn as a violet `DustParticleEffect` line (sampled every 3rd point, not every point) plus an `END_ROD` burst at the predicted landing spot.
  - **Battery**: single-resource `EnderPearlLauncherState` data component (`P7DataComponents.ENDER_PEARL_LAUNCHER_STATE`), same pattern as `ChargeLaserState` — 400 units per `power_bank` reload (sneak + right-click, not in creative), 100 units per shot flat regardless of charge level (~4 shots/bank), drives the real item durability bar via `getItemBarStep`/`getItemBarColor` exactly like the charge laser's battery does.
  - **Sounds**: three new events (`item.ender_pearl_launcher.charge/launch/reload`) in `P7Sounds` + `sounds.json`, redirected to vanilla placeholders (`block.beacon.power_select` with pitch climbing as charge builds, `item.crossbow.shoot` for the launch thunk, `block.iron_trapdoor.close` for reload) with subtitles. Dry-click/soft-click **reuses the existing `WEAPON_DRY_FIRE`** sound rather than adding a near-duplicate, following the charge laser's own precedent. No custom teleport sound — vanilla `EnderPearlEntity#onCollision` already plays one.
  - **Recipe**: `2× eye of ender + amethyst shard` top row, `2× gun barrel + power bank` middle row, `2× iron ingot + redstone` bottom row (shaped 3×3) → 1 launcher — deliberately expensive for a repositioning tool this strong.
  - **Model**: new hand-authored multi-element item model (`models/item/ender_pearl_launcher.json`, the same `minecraft:block/block` + flat-swatch-material pattern `charge_laser.json`/`glow_stick.json` use), reusing seven textures the mod already ships (no new PNGs) — dark grip, mid-grey receiver, dark barrel, a teal muzzle flare, a violet gem visible through the barrel (the eye of ender core), a gold sight rail, a yellow-gold battery indicator block.
  - **Not verified / most worth a second look**: everything (gradle can't run here), but especially: the `EnderPearlEntity(World, LivingEntity)` constructor and the plain `setVelocity(double,double,double)` call (high confidence — the latter is already proven in this repo via `GlowStickEntity#launch`, the former matches vanilla `EnderPearlItem#use`'s well-known shape from memory, not verified against a decompiled 1.21.1 jar); `ItemCooldownManager#isCoolingDown` (not otherwise used in this repo, though `#set` is, via `GlowStickItem`); and the landing-prediction sim's cheap air-check-then-raycast approach, which is a deliberate compromise (not a full per-tick raycast like `ChargeLaserItem`'s beam) that hasn't been visually checked for how well it tracks the pearl's *actual* landing spot.

## Shipped this session (glow stick — Phase 4's first player tool)

- **Glow stick** (`GlowStickItem` + `GlowStickEntity` + `GlowStickBlock`, all `common`): the doc's Phase 4 "reverse engineering" opener — the first item a player crafts rather than salvages, and the first player-facing tool overall. Cheap and disposable by design (the owner's brief: player tools have to be cool and fun on their own without trivializing the horror), so this is deliberately **not** permanent lighting:
  - **Recipe**: shaped, 3 glowstone dust + 3 sticks (`g s g` / `s g s`) → 16 glow sticks — comparable cost-per-light to vanilla torches, cheap enough to toss freely per the brief.
  - **Throw**: right-click throws one (snowball/egg-shaped `use()`, consumes 1 outside creative, small 4-tick cooldown via `ItemCooldownManager`), playing `item.glow_stick.throw`.
  - **Flight**: `GlowStickEntity extends ThrownEntity` directly (not `AbstractShellEntity` — no explosion/impact machinery needed for a light tool), gravity 0.02 vs. the vanilla-snowball-ish ~0.03 baseline, so it arcs floatier/gentler than a snowball.
  - **On block hit**: sticks to the hit face and places a `GlowStickBlock` with a `Properties.FACING` (all 6 directions, torch-like floor/wall/ceiling) computed as `hitSide.getOpposite()` — the direction from the placed block back toward its support. Plays `block.glow_stick.stick`. On an entity hit (no damage — it's a light tool) or an already-occupied face, it drops itself as a normal `ItemEntity` instead of placing anything.
  - **Burn-down**: **scheduled block ticks + an `IntProperty STAGE` (0-3)** — no block entity, per the task's own preferred option (cheaper than a `CrateBlockEntity`-style countdown here since there's nothing to persist beyond one int already living in the blockstate). `GlowStickEntity` schedules the first tick when it places the block; each `scheduledTick` steps `STAGE` up and reschedules itself (~800 ticks / 40s per stage), and `Settings.luminance(state -> GlowStickBlock.luminanceForStage(state.get(STAGE)))` maps stages 0-3 to light levels 12→9→6→3. The stage-3 tick plays `block.glow_stick.fade` and calls `World#removeBlock` directly (not `breakBlock`) so the loot table never fires — a glow stick that burns out on its own drops nothing. A player who mines it early (any stage) gets the ordinary loot-table drop instead — "breaking it while still glowing may drop it back" falls out of that distinction for free, no special-case code.
  - **Models**: new scratchpad-generated assets following the repo's established pipeline — a slim rod + brighter tip, both as a 3D item model (`models/item/glow_stick.json`, the same `minecraft:block/block` + flat-swatch-texture + shared `display` transform shape as `gun_barrel.json`/`explosive_warhead.json`) and 6 explicit per-facing block models (`models/block/glow_stick_{down,up,north,south,east,west}.json` — hand-computed axis-aligned cuboids per facing rather than blockstate `x`/`y` rotations of one shared model, to avoid guessing rotation math that can't be visually verified here) plus a small custom `GlowStickModel`/`GlowStickRenderer` Java pair (mirrors `HowitzerShellModel`/`HowitzerShellRenderer` exactly) for the flying entity, instead of a `FlyingItemEntityRenderer` — this repo has no existing precedent for that renderer's API in this Yarn version, whereas the shell-model pattern is already proven to compile here.
  - **Sounds**: three new events (`item.glow_stick.throw`, `block.glow_stick.stick`, `block.glow_stick.fade`) registered in `P7Sounds` and `sounds.json`, redirected to vanilla placeholders (`entity.snowball.throw`, `block.amethyst_block.place`, `block.glass.break` respectively) per the repo's existing placeholder-sound convention, with subtitle lang entries.
  - **Registration**: no `BlockItem` for `GlowStickBlock` — the throwable item is the only player-facing form, the block only ever appears via the entity sticking to a surface, matching the task's explicit guidance.
  - **Known gap (documented in the class doc)**: `GlowStickBlock` doesn't watch its support block — mining out the block it's stuck to leaves it floating rather than popping off like a torch would. Left out on purpose: the neighbor-update/support-check block API (`getStateForNeighborUpdate`) changed shape substantially in 1.20.5+ (gained `WorldView`/`ScheduledTickView`/`Random` params), and getting that exact signature wrong is a compile-time risk with no way to verify locally. A later pass can add it once it's checked against a real client/CI run.
  - **Not yet verified**: the six per-facing block model orientations and the item model's in-hand look are hand-reasoned from geometry, not visually tested (gradle can't run here) — worth a first look in-game before calling the art pass done.

- **Battery fire**: `FireMissionManager` shares one `FireMission` object across same-`battery()`-key tubes within 32 blocks targeting the same player, so several howitzers (or mortars) parked near each other range in together and fire for effect denser than any one tube alone. NOTE: battery-sharing is a live-scan optimization only — a world restart flattens shared missions back to independent per-tube copies, which the next scan re-shares if they're still on the same target. Not yet exercised by any in-game battery placement (no wave/dispatch code groups tubes together); proven by the mechanism, not by content.
- **Datapad inbound-fire warning generalized**: `DatapadItem.incomingFor` now scans for any `AbstractShellEntity` (not just `HowitzerShellEntity`), so the ETA/bearing warning will pick up every new munition family below once they exist.
- **MLRS / rocket artillery** (`MlrsLauncherEntity` + `MlrsRocketEntity` + `MlrsAttackGoal`): mobile Tier 3-4 rocket artillery, a `FireMissionManager` client with a wide `indirectBaseSpread` (3x the howitzer's) and `battery()` opted out (mobile pieces fire alone per the doc's platform split). Fires a 6-rocket ripple staggered 4 ticks apart, each independently scattered inside a widened spread, then a long reload — the doc's "stutter of launches... wall of impacts arriving together." Registered end to end (entity/attributes, spawn egg, lang, loot table); model/renderer **reuse the howitzer chassis and howitzer-shell geometry as a placeholder** (documented in the model classes) rather than a bespoke rocket-rack/finned-rocket silhouette — a real art pass is still open.
- **Guided missiles** (`MissileLauncherEntity` + `GuidedMissileEntity` + `MissileAttackGoal`): Tier 4-5 mobile precision artillery — the doc's "deliberate inversion of unguided rockets." Fires a near-flat, low-gravity missile that steers its own velocity toward a live target each tick within a limited turn rate (`GuidedMissileEntity.steerToward`), but **only when the firing mission was currently spotted** (`FireMission.targetPlayerId()`, a new getter) — an unobserved mission still fires the missile dumb at the stale point, so losing the observer degrades a missile exactly like every cheaper tube. Tiny 4-round magazine, ~20s reload, opts out of battery sharing (rare and expensive, fires alone). Same placeholder-geometry approach as the MLRS (reuses the howitzer chassis + howitzer-shell model), registered end to end.
- **Naval bombardment**: `GunboatEntity` now implements `IndirectFireUnit` and gets a new `NavalBombardmentGoal` (lower priority than its existing `DeckGunAttackGoal`, so it only actually starts when the deck gun has no line-of-sight target of its own — the `LOOK`-control conflict does the arbitration). Fires the same `HowitzerShellEntity` the deck gun's self-observed arc mode already uses, through the full `FireMissionManager` loop (ranging, CEP, battery-opt-out since it's a mobile hull that "reposition[s] along the coast"). **Bonus fix while in this file**: `DeckGunAttackGoal.fireArcingShell`'s own self-observed mode also had the naive `dx / FLIGHT_TICKS` ballistic backfill (the same flaw the mortar had) — switched to the shared `BallisticSolver` too, so both the manager-assigned and self-observed naval bombardment paths land correctly at range.
- **Close air support** (`BombEntity` + `CasBombingGoal`, wired onto the existing `GunshipEntity`): a new `FireMissionManager` client that, whenever the belly cannon has no live target of its own, flies to a point above a purely indirect designation and releases a 4-bomb stick a few ticks apart, offset along its own current heading so the stick walks a line across the target rather than clustering — the doc's "a stick of bombs walked along a line across the target on a diving pass." No new aircraft entity: the doc explicitly frames CAS as "a fixed-wing or the gunship," and `GunshipEntity`'s own class doc already flagged the bombing run as wired in later — this is that pass. Bombs draw from the gunship's existing cannon magazine. Lower priority than the belly cannon's `BurstGunAttackGoal` (same arbitration pattern as the other new goals this session).
- **Terrain saturation / erosion accumulator** (`TerrainSaturation`, a new `ProgramDirectorState` sibling organ next to `FireMissionManager`, ticked and NBT-persisted the same way): the doc's §5a cumulative-erosion model. Every shell impact (`AbstractShellEntity.onImpact`) feeds a coarse, lazily-decaying per-column grid (4x4-block cells, decay computed on read rather than swept every tick) via a `saturationWeight()` hook — 1.0 for mortar/rocket/bomb, 2.0 for the howitzer/missile ("heavier munitions add more saturation per hit"). Once a cell's saturation crosses a block's own blast-resistance-scaled threshold, a small footprint around the impact (3x3 columns, 2 Y layers) steps **at most one stage per block per impact** through a staged downgrade table (stone→cobblestone→gravel→sand→gone, grass/dirt→coarse dirt→sand→gone, snow→gone) — restrained per round, only sustained fire on one spot reaches the late stages, matching the doc's "no instant craters" rule. **Scope limit (documented in the class doc):** the downgrade table only covers the common stone/soil families; an unlisted block falls back to a coarse "pulverize past a high threshold" rule rather than a full staged chain — a fuller per-block table is a later content pass. Untested for real bombardment feel/pacing (thresholds are a first guess, same "needs playtesting" caveat as the CEP constants).
- **Off-screen statistical resolution** (`FireMissionManager.resolveOffscreenMissions`, doc §7): a mission whose tube's chunk isn't loaded (so its attack goal can't tick) now rolls a shot statistically on a coarse ~10s cadence instead of just sitting idle — a scattered impact point off the mission's own CEP, real block/entity damage if the target's chunk happens to be loaded (e.g. a different player standing at the target while the gun is far off), and always an acoustic report so a distant player hears "a barrage over the horizon." Added `IndirectFireUnit#indirectImpactPower()` (default method, overridden on the howitzer/gunboat/missile launcher to match their real shell's explosion power) so the manager has something to hand `World#createExplosion` with no real shell entity to ask. **Documented gaps, not silent bugs:** off-screen shots don't debit the tube's own onboard magazine (inaccessible on an unloaded entity — fires "for free" rather than truly starving out); a shot rolled while the *target* chunk is also unloaded has no physical effect at all rather than deferring/replaying once that chunk later loads (the doc's fuller "applies... if and when that area loads" behavior); and because a dead tube and a merely-unloaded one are indistinguishable via `world.getEntity()` (a pre-existing ambiguity already flagged in `pruneMissions`), a tube that dies mid-mission can fire one phantom off-screen shot before its mission ages out (~10s grace window).
- **Research tree — first cut** (`ResearchTree`, a new `ProgramDirectorState` sibling; `PsionicResearchBlock`/`PsionicResearchBlockEntity`, copy-pasted from `ProbeCoreBlock`/`ProbeCoreBlockEntity` per the doc's own recommendation): proves the doc's whole loop end to end — `RESEARCH_TREE.md` §10 build-order step 2 — with a **single hardcoded node** (`tier2_hardware`) instead of the full data-driven node table. Once a Program core site exists, the building places itself nearby (directly, not grown incrementally through `ConstructionSite`), then feeds a step off the ledger (`tryConsume`, mirroring `ConstructionSite.BUILD_STEP_COST`'s shape) on a cadence; damaging the building (`isUnderAttack`) pauses feeding without reversing progress; destroying it (`onBuildingDestroyed`, hooked off `PsionicResearchBlock.onStateReplaced`) halves progress and clears the building, forcing a fresh placement before research resumes; completing the node flips it `UNLOCKED`. **Deliberately not wired to anything yet** — this is the explicitly-scoped-down "first cut" the task asked for, not the full system:

  - No adaptive-focus scoring pass (§4, `counterPressure`/`recordScan` hookup) — meaningless with only one node to score.

## Review fixes applied (2026-07-14 Fable sweep, artillery + research-tree batch)

A second Fable review pass over the artillery/research-tree batch (`9a9b305..69188e9`) found 10 issues; 9 are fixed, 1 is deliberately left as documented dead state rather than papered over. Gradle still can't compile locally — these are hand-reasoned against the existing patterns, unverified at runtime.

- **Off-screen missions died after one shot** (`FireMissionManager`, HIGH): `resolveStatisticalShot` now refreshes `mission.lastTouchTick` when a shot actually rolls, so a sustained off-screen barrage doesn't get pruned by the same `MISSION_DROP_TICKS` idle TTL that governs an abandoned mission (they were both 200 ticks, so a mission fired exactly once then aged out on the next scan). `offscreenCooldown` is now persisted in NBT too, so a restart mid-barrage resumes the fire clock instead of resetting to a full interval while the (until-now-unrefreshed) idle clock kept running — which could prune the mission before its delayed next shot ever fired.
- **Battery fire almost never engaged** (`FireMissionManager`, HIGH): `findBatteryMate` now also checks a `liveTubes` map built fresh each `assignMissions` pass (every tube seen this scan, not just ones that already had a mission as of the *previous* `pruneMissions` pass). Two idle tubes of the same battery assigned in the same scan now correctly merge onto one shared `FireMission` instead of each starting an independent one.
- **Shared battery missions thrashed** (`FireMissionManager`, MEDIUM): `applyDesignation` now supersedes (skips) a lower-priority, unspotted designation write when the mission is currently observed and was touched more recently than a full scan interval ago — i.e. some other tube is self-observing it live every tick. Previously an external scan's counter-battery/dwell designation clobbered `observed`/the ranging anchor every ~1s even while a battery-mate had real eyes on, pinning ranging at wide forever. Single-tube missions are unaffected once nothing self-observes for a full scan interval.
- **Off-screen shots fed the wrong number into terrain erosion** (`FireMissionManager` / `IndirectFireUnit`, MEDIUM): off-screen `recordImpact` calls were passing `impactPower` (explosion blast power, 2.0-3.4) into the 3rd param, which is actually the saturation *weight* (1.0-2.0). Added `IndirectFireUnit#indirectSaturationWeight()` (mirrors `AbstractShellEntity#saturationWeight()`, overridden to 2.0 on the howitzer/gunboat/missile-launcher to match their real shell), stored on `FireMission`, persisted, and used instead.
- **ResearchTree did synchronous chunk loads from the Director tick** (`ResearchTree`, HIGH): added a `PLACEMENT_RETRY_TICKS` (200-tick) cooldown so `tryPlaceBuilding` — and the up-to-8 force-loaded chunks `pickBuildingSite` tries per call — no longer runs every single tick while no candidate site validates. Once placed, `tick()` now checks `world.getChunk(cx, cz, ChunkStatus.FULL, false) == null` before touching `world.getBlockEntity`, and simply skips the tick if the building's chunk isn't loaded, instead of `getBlockEntity` silently force-loading it every tick as a hidden chunkloader.
- **ResearchTree re-placed the building instantly with nothing left to research** (`ResearchTree`, LOW): the same `buildingPos == null` branch now also checks `nodeStatus != UNLOCKED` before attempting placement (and shares the new placement cooldown above).
- **A scrambled gunboat/gunship kept firing** (`NavalBombardmentGoal`, `CasBombingGoal`, MEDIUM): both goals' `canStart()` now gate on `shooter.isScrambled()`, matching `GunAttackGoal`'s existing check. `CasBombingGoal.shouldContinue()` also checks it directly so a scramble cuts an in-progress bombing run short instead of letting the stick finish.
- **`CasBombingGoal` had no `stop()` reset** (LOW): added a `stop()` override that clears `bombsLeft`/`stickAim`/`runMission` and halts navigation, so a goal preempted mid-stick doesn't resume with stale aim/mission state on its next run.
- **`GuidedMissileEntity.guidanceTargetId` wasn't persisted** (LOW): added `writeCustomDataToNbt`/`readCustomDataFromNbt` (UUID round-trip), so a missile mid-flight when its chunk unloads or the server restarts keeps homing instead of silently flying dumb from then on.
- **`PsionicResearchBlockEntity.hp` is dead state** (LOW, DEFERRED): confirmed nothing decrements `hp` — same as `ProbeCoreBlockEntity`, which it was copy-pasted from and which already documents `hp` as "scaffolding for a future damage mechanic."
