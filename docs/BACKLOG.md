## Shipped this session (charge laser — Phase 4's marquee weapon)

- **Charge laser** (`item.ChargeLaserItem`, all `common`): a long-range multitool, explicitly *not* the anti-armor answer. Shreds light/small drones, is a deliberately bad battery-wasting trade against armored vehicles, drills faraway blocks at range respecting hardness, and doubles as an ignition source (fire, TNT priming, ammo/magazine cook-off).
  - **Firing**: the bow/trident `use()` + `usageTick()` idiom (72000-tick max use, gated open/closed each tick by battery/heat/lens). `use()` starts the beam; sneak + right-click instead reloads from a `power_bank` in the inventory. `usageTick` raycasts from the eyes with `ProjectileUtil.getCollision` (range 30), draws a violet `DustParticleEffect` beam every 2 ticks, and either damages the hit `LivingEntity` (every 4th tick, `BASE_DAMAGE_PER_APPLICATION` 2.0f) or advances ranged-mining progress on the hit block.
  - **Damage routing / the melts-small-tickles-large profile**: added `ArmorProfile.DamageClass.ENERGY` and an `ENERGY` multiplier to all four profiles (UNARMORED 1.6, LIGHT 1.3, ARMORED_VEHICLE 0.2, HEAVY_HULL 0.15) — the mirror image of `BALLISTIC`. A new datapack damage type `program7:laser` (`P7DamageTypes.LASER`) is what `ProgramDroneEntity#classify` keys off of, so the profile falls out of the *existing* typed-armor math, no per-entity special-casing. **Reclassified `ReconHelicopterEntity` from `LIGHT` to `ARMORED_VEHICLE`** to match the design brief's explicit "Tier 3 armored" listing (heavy attack drone/IFV/gunboat/recon helicopter/battery center) — it already read as "heavier hull" in its own doc comment, so this was arguably a pre-existing inconsistency, not a new one. Side effect: the recon helicopter is now also tougher against ballistic/melee generally, not just the laser.
  - **Cook-off / TNT / magazines**: block hits check for `TntBlock` (removes + `TntBlock.primeTnt`) and `CargoBlock` (new public `igniteExternally`, reuses the existing private `cookOff` blast — no reinvented blast code) before falling through to mining. Dwelling on a burnable block occasionally lays `Blocks.FIRE` on top for area denial, gated on `Program7.CONFIG.terrainDestruction` + `DO_MOB_GRIEFING` (mirrors `MineResourceGoal`/`AttackDroneEntity`'s existing gates). A laser kill on a drone still carrying onboard rounds (`getMagazineSize() > 0`) detonates in `ProgramDroneEntity#onDeath`, scaled by however many rounds were left — chains naturally into anything else nearby via the normal explosion, no extra bookkeeping.
  - **Three resources, one data component**: `ChargeLaserState` (battery ticks / heat ticks / overheated latch / lens wear), the mod's first use of a custom **data component** (`P7DataComponents.CHARGE_LASER_STATE`, registered directly against the static `Registries.DATA_COMPONENT_TYPE` registry rather than an `architectury` `DeferredRegister` — that registry has no `RegistryKeys` constant to defer against). Battery (120 ticks/~6s per `power_bank`) drives the item's real durability bar via `getItemBarStep`/`getItemBarColor` (not `Damage`/`maxDamage` — deliberately avoided that vanilla component so Mending/anvil interactions can't "free-charge" the battery). Heat (400 ticks/~20s to overheat, vents at 2/tick while idle via `inventoryTick`) drives a new client-only HUD bar (`ChargeLaserHud`, reads the held stack's component directly each frame — no network payload needed, unlike the psionic interference overlay). Lens wear (24000 ticks, ~200 batteries) locks the trigger at zero and is repaired via a new crafting-grid `LensRepairRecipe` (`SpecialCraftingRecipe` + `SpecialRecipeSerializer`, the repo's first custom recipe type — laser + 1-8 amethyst shards, each restoring 1/8 of full wear, output is a `copy()` of the input laser with only `lensWear` changed so battery/heat carry through).
  - **Noise**: reports to `ProgramAcoustics.reportNoise` every 20 fired ticks at loudness 0.5 — bow-level, below whatever loudness the mod's eventual firearms land at (nothing calls `reportNoise` for gunfire yet — only block-breaking does today, see `Program7.java`).
  - **Model**: a new hand-authored multi-element item model (`models/item/charge_laser.json`, the `minecraft:block/block` + flat-swatch-material pattern `gun_barrel.json`/`glow_stick.json` already use, not a Java entity model — this is a pure held item, no thrown/placed form) — dark receiver, mid-grey barrel shroud, a violet amethyst lens block, a bright lavender emitter tip, a cyan power-cell block, gold trim/sight rail. Two new flat-color material textures (`mat_7b4fae.png` violet, `mat_d9a6ff.png` lavender) generated via a scratchpad PNG-writer script mirroring `tools/render_models.py`'s `write_png`; everything else reuses textures the mod already ships. Custom (non-generic) `display` transforms tuned so the barrel reads as pointing forward in first/third person, unlike the shared copy-paste template most salvage items use.
  - **Sounds**: five new events (`item.charge_laser.spinup/beam_loop/overheat/reload/lens_warn`) in `P7Sounds` + `sounds.json`, redirected to vanilla placeholders (`block.beacon.activate`, `block.conduit.ambient`, `block.fire.extinguish`, `block.iron_trapdoor.close`, `block.amethyst_block.chime`) with subtitles. ## Shipped this session (glow stick — Phase 4's first player tool)

- **Glow stick** (`GlowStickItem` + `GlowStickEntity` + `GlowStickBlock`, all `common`): the doc's Phase 4 "reverse engineering" opener — the first item a player crafts rather than salvages, and the first player-facing tool overall. Cheap and disposable by design (the owner's brief: player tools have to be cool and fun on their own without trivializing the horror), so this is deliberately **not** permanent lighting:
  - **Recipe**: shaped, 3 glowstone dust + 3 sticks (`g s g` / `s g s`) → 16 glow sticks — comparable cost-per-light to vanilla torches, cheap enough to toss freely per the brief.
  - **Throw**: right-click throws one (snowball/egg-shaped `use()`, consumes 1 outside creative, small 4-tick cooldown via `ItemCooldownManager`), playing `item.glow_stick.throw`.
  - **Flight**: `GlowStickEntity extends ThrownEntity` directly (not `AbstractShellEntity` — no explosion/impact machinery needed for a light tool), gravity 0.02 vs. the vanilla-snowball-ish ~0.03 baseline, so it arcs floatier/gentler than a snowball.
  - **On block hit**: sticks to the hit face and places a `GlowStickBlock` with a `Properties.FACING` (all 6 directions, torch-like floor/wall/ceiling) computed as `hitSide.getOpposite()` — the direction from the placed block back toward its support. Plays `block.glow_stick.stick`. On an entity hit (no damage — it's a light tool) or an already-occupied face, it drops itself as a normal `ItemEntity` instead of placing anything.
  - **Burn-down**: **scheduled block ticks + an `IntProperty STAGE` (0-3)** — no block entity, per the task's own preferred option (cheaper than a `CrateBlockEntity`-style countdown here since there's nothing to persist beyond one int already living in the blockstate). `GlowStickEntity` schedules the first tick when it places the block; each `scheduledTick` steps `STAGE` up and reschedules itself (~800 ticks / 40s per stage), and `Settings.luminance(state -> GlowStickBlock.luminanceForStage(state.get(STAGE)))` maps stages 0-3 to light levels 12→9→6→3. The stage-3 tick plays `block.glow_stick.fade` and calls `World#removeBlock` directly (not `breakBlock`) so the loot table never fires — a glow stick that burns out on its own drops nothing. A player who mines it early (any stage) gets the ordinary loot-table drop instead — "breaking it while still glowing may drop it back" falls out of that distinction for free, no special-case code.
  - **Models**: new scratchpad-generated assets following the repo's established pipeline — a slim rod + brighter tip, both as a 3D item model (`models/item/glow_stick.json`, the same `minecraft:block/block` + flat-swatch-texture + shared `display` transform shape as `gun_barrel.json`/`explosive_warhead.json`) and 6 explicit per-facing block models (`models/block/glow_stick_{down,up,north,south,east,west}.json` — hand-computed axis-aligned cuboids per facing rather than blockstate `x`/`y` rotations of one shared model, to avoid guessing rotation math that can't be visually verified here) plus a small custom `GlowStickModel`/`GlowStickRenderer` Java pair (mirrors `HowitzerShellModel`/`HowitzerShellRenderer` exactly) for the flying entity, instead of a `FlyingItemEntityRenderer` — this repo has no existing precedent for that renderer's API in this Yarn version, whereas the shell-model pattern is already proven to compile here.
  - **Sounds**: three new events (`item.glow_stick.throw`, `block.glow_stick.stick`, `block.glow_stick.fade`) registered in `P7Sounds` and `sounds.json`, redirected to vanilla placeholders (`entity.snowball.throw`, `block.amethyst_block.place`, `block.glass.break` respectively) per the repo's existing placeholder-sound convention, with subtitle lang entries.
  - **Registration**: no `BlockItem` for `GlowStickBlock` — the throwable item is the only player-facing form, the block only ever appears via the entity sticking to a surface, matching the task's explicit guidance.
  - **Known gap (documented in the class doc)**: `GlowStickBlock` doesn't watch its support block — mining out the block it's stuck to leaves it floating rather than popping off like a torch would. Left out on purpose: the neighbor-update/support-check block API (`getStateForNeighborUpdate`) changed shape substantially in 1.20.5+ (gained `WorldView`/`ScheduledTickView`/`Random` params), and getting that exact signature wrong is a compile-time risk with no way to verify locally. A later pass can add it once it's checked against a real client/CI run.
  - **Not yet verified**: the six per-facing block model orientations and the item model's in-hand look are hand-reasoned from geometry, not visually tested (gradle can't run here) — worth a first look in-game before calling the art pass done.

- **Terrain saturation / erosion accumulator** (`TerrainSaturation`, a new `ProgramDirectorState` sibling organ next to `FireMissionManager`, ticked and NBT-persisted the same way): the doc's §5a cumulative-erosion model. Every shell impact (`AbstractShellEntity.onImpact`) feeds a coarse, lazily-decaying per-column grid (4x4-block cells, decay computed on read rather than swept every tick) via a `saturationWeight()` hook — 1.0 for mortar/rocket/bomb, 2.0 for the howitzer/missile ("heavier munitions add more saturation per hit"). Once a cell's saturation crosses a block's own blast-resistance-scaled threshold, a small footprint around the impact (3x3 columns, 2 Y layers) steps **at most one stage per block per impact** through a staged downgrade table (stone→cobblestone→gravel→sand→gone, grass/dirt→coarse dirt→sand→gone, snow→gone) — restrained per round, only sustained fire on one spot reaches the late stages, matching the doc's "no instant craters" rule. **Scope limit (documented in the class doc):** the downgrade table only covers the common stone/soil families; an unlisted block falls back to a coarse "pulverize past a high threshold" rule rather than a full staged chain — a fuller per-block table is a later content pass. ## Review fixes applied (2026-07-14 Fable sweep, artillery + research-tree batch)

A second Fable review pass over the artillery/research-tree batch (`9a9b305..69188e9`) found 10 issues; 9 are fixed, 1 is deliberately left as documented dead state rather than papered over. Gradle still can't compile locally — these are hand-reasoned against the existing patterns, unverified at runtime.

- **Off-screen missions died after one shot** (`FireMissionManager`, HIGH): `resolveStatisticalShot` now refreshes `mission.lastTouchTick` when a shot actually rolls, so a sustained off-screen barrage doesn't get pruned by the same `MISSION_DROP_TICKS` idle TTL that governs an abandoned mission (they were both 200 ticks, so a mission fired exactly once then aged out on the next scan). `offscreenCooldown` is now persisted in NBT too, so a restart mid-barrage resumes the fire clock instead of resetting to a full interval while the (until-now-unrefreshed) idle clock kept running — which could prune the mission before its delayed next shot ever fired.
- **Battery fire almost never engaged** (`FireMissionManager`, HIGH): `findBatteryMate` now also checks a `liveTubes` map built fresh each `assignMissions` pass (every tube seen this scan, not just ones that already had a mission as of the *previous* `pruneMissions` pass). Two idle tubes of the same battery assigned in the same scan now correctly merge onto one shared `FireMission` instead of each starting an independent one.
- **Shared battery missions thrashed** (`FireMissionManager`, MEDIUM): `applyDesignation` now supersedes (skips) a lower-priority, unspotted designation write when the mission is currently observed and was touched more recently than a full scan interval ago — i.e. some other tube is self-observing it live every tick. Previously an external scan's counter-battery/dwell designation clobbered `observed`/the ranging anchor every ~1s even while a battery-mate had real eyes on, pinning ranging at wide forever. Single-tube missions are unaffected once nothing self-observes for a full scan interval.
- **Off-screen shots fed the wrong number into terrain erosion** (`FireMissionManager` / `IndirectFireUnit`, MEDIUM): off-screen `recordImpact` calls were passing `impactPower` (explosion blast power, 2.0-3.4) into the 3rd param, which is actually the saturation *weight* (1.0-2.0). Added `IndirectFireUnit#indirectSaturationWeight()` (mirrors `AbstractShellEntity#saturationWeight()`, overridden to 2.0 on the howitzer/gunboat/missile-launcher to match their real shell), stored on `FireMission`, persisted, and used instead.
- **ResearchTree did synchronous chunk loads from the Director tick** (`ResearchTree`, HIGH): added a `PLACEMENT_RETRY_TICKS` (200-tick) cooldown so `tryPlaceBuilding` — and the up-to-8 force-loaded chunks `pickBuildingSite` tries per call — no longer runs every single tick while no candidate site validates. Once placed, `tick()` now checks `world.getChunk(cx, cz, ChunkStatus.FULL, false) == null` before touching `world.getBlockEntity`, and simply skips the tick if the building's chunk isn't loaded, instead of `getBlockEntity` silently force-loading it every tick as a hidden chunkloader.
- **ResearchTree re-placed the building instantly with nothing left to research** (`ResearchTree`, LOW): the same `buildingPos == null` branch now also checks `nodeStatus != UNLOCKED` before attempting placement (and shares the new placement cooldown above).
- **A scrambled gunboat/gunship kept firing** (`NavalBombardmentGoal`, `CasBombingGoal`, MEDIUM): both goals' `canStart()` now gate on `shooter.isScrambled()`, matching `GunAttackGoal`'s existing check. `CasBombingGoal.shouldContinue()` also checks it directly so a scramble cuts an in-progress bombing run short instead of letting the stick finish.
- **`CasBombingGoal` had no `stop()` reset** (LOW): added a `stop()` override that clears `bombsLeft`/`stickAim`/`runMission` and halts navigation, so a goal preempted mid-stick doesn't resume with stale aim/mission state on its next run.
- **`GuidedMissileEntity.guidanceTargetId` wasn't persisted** (LOW): added `writeCustomDataToNbt`/`readCustomDataFromNbt` (UUID round-trip), so a missile mid-flight when its chunk unloads or the server restarts keeps homing instead of silently flying dumb from then on.
- **`PsionicResearchBlockEntity.hp` is dead state** (LOW, DEFERRED): confirmed nothing decrements `hp` — same as `ProbeCoreBlockEntity`, which it was copy-pasted from and which already documents `hp` as "scaffolding for a future damage mechanic." Neither building has *any* damage-dealing hook in the codebase today (only `markDamaged`, which stamps the under-attack window, not `hp`), so wiring real damage into just this one building is a bigger design task than this pass (what deals the damage? explosions? entity attacks? both buildings?) rather than a small fix. Left as explicitly-documented dead state (see the class doc) instead of silently shipping it. **Open follow-up**: design and wire an actual damage source for `ProbeCoreBlockEntity`/`PsionicResearchBlockEntity`'s shared `hp` model, or remove the field if it's not going to be used.

## Environment notes for resuming

- Gradle can't run locally (the proxy blocks the distribution download). CI is compile-only — verify via GitHub Actions on the branch, never locally.
- 1.21.1 Yarn API gotchas: `onStateReplaced` is the 5-arg overload; recipe result is `{"id","count"}` and ingredients use the object form `{"item"}` / `{"tag"}`; data folders are singular (`recipe` / `loot_table` / `advancement`); `DustParticleEffect(Vector3f, float)`.
- More gotchas found this session (verified against raw Yarn 1.21.1 tiny mappings, not runtime): `net.minecraft.recipe.input.CraftingRecipeInput` (own package, not `recipe`) exposes `getStacks()`/`getStackInSlot(x, y)`/`getWidth()`/`getHeight()`, not an `Inventory`; a `SpecialCraftingRecipe` subclass needs `CraftingRecipeCategory` in its constructor and its recipe JSON needs a mandatory `"category"` field (vanilla special recipes all carry one, e.g. `"category": "misc"` — plain shaped/shapeless recipes in this repo omit it and that's fine, it's optional there); `Item.appendTooltip`'s context param is `Item.TooltipContext` and the type param is `net.minecraft.item.tooltip.TooltipType`; `Item#isItemBarVisible`/`getItemBarStep`/`getItemBarColor` are the hook for a *custom* item-bar-shaped display that isn't real vanilla `Damage`/`maxDamage` durability; `Registries.DATA_COMPONENT_TYPE` is a static/built-in registry (register with plain `Registry.register`, not a `RegistryKeys`-keyed `DeferredRegister` — no such `RegistryKeys` constant was found for it); `PacketCodecs.codec(Codec<T>)` bridges a DFU `Codec` into a `PacketCodec` for a data component's network sync.
- Model pipeline: scratchpad Python generators (`gunship_sculpt.py` / `detailed_ifv.py` / `detailed_cargo.py`) → source geometry + UV atlas + texture + Java `getTexturedModelData()`. Front = -Z, up = -Y (Minecraft convention).
- Commit trailer convention is set by the environment; never put a model identifier in commits, PRs, or code.
